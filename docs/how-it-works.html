How the WhatsApp training agent works

One WhatsApp number that answers questions about 67 real Cruz Roja courses, lets people browse a tappable menu, and captures enrolment leads into the dashboard — without ever inventing a price.

Tapping is instant and free

Menu taps are answered straight from the database — no embedding call, no model call. The catalogue is cached for five minutes, so a tap costs a dictionary lookup.

Typing goes through retrieval

Free text is embedded, matched against the course cards, and answered by the model using only what came back. Roughly three to five seconds.

The agent knows what you are looking at

Ask “¿incluye manual?” right after opening the BLS card and it answers about BLS. The card being viewed is pinned into the context, so follow-ups don’t need to repeat the course name.

It never quotes a price it cannot trace

Every amount in a generated answer is checked against the courses table before sending. An untraceable figure means the reply is replaced with stored facts.

2

How a message travels

Meta allows about two seconds to acknowledge a webhook before it assumes the endpoint is broken and redelivers. So the webhook does almost nothing: it proves the message is genuine, hands it to a background task, and returns.

Arrival≤ 2 s budget
POST /webhook→ verify HMAC signature→ parse_webhook→ 200 OK→ background task
Tap~200 ms · $0
crs:HP038→ parse_action→ read courses (cached)→ render card→ send
Typed~3–5 s
embed question→ vector + name search→ assemble context→ model writes reply→ verify prices→ send

Why retrieval runs two searches

Vector search is good at meaning: “qué hago si alguien se está ahogando” finds the CPR and airway course without sharing a word with it. Name search is good at exact things: course codes and acronyms, where every trauma card looks alike to an embedding. Each catches what the other misses, and the results are merged with the name hit ranked higher.

If the best match scores below 0.55, the agent says it doesn’t have that information rather than improvising, and writes the question to unanswered_questions — the list Cruz Roja works through to improve their own material.

4

Sign-up, and what happens when it’s interrupted

The flow collects five fields and pushes the lead to the dashboard. The part that matters commercially is what it does when someone asks a question halfway through.

CHATTING→ ENROLL_COURSE→ ENROLL_NAME→ ENROLL_EMAIL→ ENROLL_PHONE→ ENROLL_ADDRESS→ pushed to dashboard
Interruption any question mid-flow→ answered with the course pinned→ same field asked again→ state & draft untouched

A lead who asks “¿el curso incluye manual?” while typing their email is not a lead you want to drop, and they are not answering the question you asked. The agent detects that the message is a question, answers it, then repeats the field it was waiting on. Nothing collected so far is lost, and the flow does not restart.

Starting from a course card skips the first step entirely — the course is already known, so it goes straight to asking for a name. Email and phone are validated before being stored, and the phone check mirrors the dashboard’s own toLocalPhone() so a number accepted here can never be rejected there.

The state moves to CHATTING before the dashboard push, so a duplicate webhook delivery from Meta cannot submit the same lead twice.

5

What keeps it honest

Six rails. Four come from the client's own data guide; two are ordinary production hygiene the first version was missing.

Webhook signature

The webhook URL is public — anyone who finds it can POST a fake customer message. Every delivery is now checked against Meta’s HMAC over the raw body, in constant time.

channels/whatsapp/verify.py

Price verification

Every amount in a generated reply must trace back to the courses table. If one doesn’t, the model’s text is discarded and a card built from stored facts is sent instead. A wrong course suggestion is recoverable; a wrong price is a commercial problem.

core/generation.py · verify_prices()

Compliance flags

Courses carrying a known data quirk inject a rule into the prompt. HP014 and HP015 share one description verbatim, so the agent may use it but must not explain the difference between them — it routes that to the team.

core/prompts.py · FLAG_NOTICES

Never close a door

Class size is not a rejection: a 30-person company gets offered a second group or a private booking, never a “no”. Minimum enrolment is never used to say a course won’t run, and start dates are always confirmed by the team.

core/prompts.py · SYSTEM

Confidence floor

Below 0.55 similarity the agent says it doesn’t know and logs the question, rather than filling the gap with something plausible.

core/retrieval.py · CONFIDENCE_FLOOR

Rate limit & takeover

Twenty messages per minute per number caps runaway cost. Setting human_takeover on a lead makes the bot go silent so a person on the dashboard can reply instead.

core/conversation.py

One rail is not armed yet

META_APP_SECRET is not set in .env, so signature verification currently logs a warning and lets requests through. Copy the App Secret from Meta → App → Settings → Basic before this goes live; the code enforces it as soon as the value exists.

6

The data, and how it gets in

The client sends a spreadsheet. It arrives human-typed: prices written three different ways, course names up to 66 characters, the same category spelled with trailing spaces. Normalisation happens once, at ingest.

Ingestpython ingest.py
juptr_rc_courses.csv→ normalise→ build 71 cards→ embed (768-dim)→ courses + course_chunks

Two tables, two jobs

courses holds one structured row per course and is the source of truth for anything the agent must not improvise — price, hours, prerequisites, credential. Menus read from it, and generated answers are checked against it.

course_chunks holds one readable card per course plus four institutional cards (contact details, membership, hospital services), each with a 768-dimension embedding and an HNSW cosine index. Questions search this.

Decisions made once, at normalise time

  • Prices — 755 becomes a number plus the display text “$755 MXN por persona”. The five package and instalment programmes get no number at all, because there isn’t a single one to quote.
  • Menu labels — a course’s own acronym wins (BLS, PHTLS, DAMP-B); otherwise the name is trimmed on a word boundary to fit 24 characters.
  • Category — GP009 carries a General Public prefix but is a 920-hour paid diploma, so it is filed with the diplomas, exactly as the data guide instructs.

Two columns still to come from the client

Content_Modules and Learning_Objectives were truncated in the PDF export, so they are not loaded. The pipeline already has columns for them — when the original .xlsx arrives, add them to the CSV and re-run ingest.py. Until then the agent answers “what is actually covered?” from the short description.

Working inside the monorepo

This agent was built to the same separation your senior's structure uses, so moving it in is a copy per folder rather than a rewrite. Here is where each piece lands.

The four rules that structure enforces

  1. core/ imports no vendor SDK. It asks for “something that can generate text”; providers/ decides what that is. There is a lint rule in the monorepo that fails the build if this is broken — it is why the AWS migration is a config change.
  2. Only config reads the environment. Everything else imports from it, so a missing key fails at boot with a clear message, not at 2am on a live webhook.
  3. The API never does slow work. Anything that takes seconds belongs in the worker. In this repo that is a FastAPI background task; in the monorepo it is a queue job — the function body is the same either way.
  4. Prices are verified, never recalled. Look the number up by course id before it goes out, whichever channel is asking.

Your first pull request into that repo

  1. 1Port the schema first packages/db/prisma/schema.prisma gains courses, course_chunks and unanswered_questions. The card similarity search is hand-written SQL under prisma/sql/ — Prisma cannot express it.
  2. 2Add the index assertion assertIndexes.ts already exists for exactly this reason: a routine migration can silently drop the HNSW index and nothing visibly breaks — search just gets slow and expensive.
  3. 3Move providers before core Port embeddings and llm first, so the core files you port next have something to import that isn’t vendor-specific.
  4. 4Keep answer() as the single entry point The web widget on the WordPress site will call the same function. Don’t let WhatsApp-specific formatting leak into it — that belongs in packages/channels/whatsapp/format.ts.
  5. 5Add the menu tree to evals evals/questions.yaml should include the real questions this agent gets — prices, requirements, group bookings — so a model or prompt change can be measured instead of guessed at.

Running it

From a clean checkout, in order.

# 1. install
pip install -r requirements.txt

# 2. build the catalogue CSV from the client's sheet (already committed)
python scripts/build_catalog_csv.py

# 3. create the tables — idempotent, safe to re-run
#    paste schema.sql into the Supabase SQL editor

# 4. load 67 courses and embed 71 cards (~30 s)
python ingest.py

# 5. check the whole flow without touching the DB, model or Meta
python scripts/selftest.py

# 6. see a live transcript — nothing is sent to WhatsApp
python scripts/simulate_chat.py

# 7. serve
uvicorn server:app --reload

Environment

Required: META_ACCESS_TOKEN, META_PHONE_NUMBER_ID, META_VERIFY_TOKEN, DATABASE_URL, GEMINI_API_KEY. Strongly recommended: META_APP_SECRET. Optional: DASHBOARD_URL and INGEST_TOKEN for lead push, CHAT_PROVIDER=claude to switch models.

Deployment is unchanged — server.py still exposes app, so the existing Render start command keeps working. Run with WEB_CONCURRENCY=1: per-phone locking is in-process.
